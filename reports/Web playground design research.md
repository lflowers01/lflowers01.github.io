# Build a personal web worth exploring

**Research date:** October 18, 2026. **For:** Lucas Flowers. **Scope:** inspiration, observed examples and implementation planning; no website implementation, deployment or webring submission.

The strongest version of this site would combine **one consistent visual world, one signature interactive artwork and a few genuinely personal things to read**. Your ideas already fit together: a dithered portrait, an ASCII robot, a project shelf, short public thoughts, a music window and a shared “boop the robot” total could feel like parts of the same place. The closest documented reference is **apvl.dev**, which combines dithering, music and Markdown thoughts; **Webamp** supplies the actual Winamp-style player; **Poolsuite** demonstrates a coherent music-centered desktop. A static site can handle most of this, with one small external API/database for the shared number. This report proposes alternatives rather than selecting your final aesthetic. It also separates what researchers fetched, what creators documented, what REA actually observed and what we are suggesting for your own design.

### What reverse engineering established

**Webamp is a reusable interaction, not merely a visual reference.** REA captured its playlist/equalizer controls, track labels, play/pause/stop buttons, seeking/volume/balance sliders and skin menu. The DOM included canvas elements and embedded PNG skin resources; successful responses included application JavaScript, a Butterchurn-related bundle and a demo MP3 range response. A second run clicked the observed `#play` control and captured changed numeric audio readout text. This proves resource loading, interaction dispatch and a UI update; **no audio was recorded or listened to**, so it does not prove audible playback. The official project separately documents that Webamp reimplements Winamp in the browser and supports skins. ([Live target](https://webamp.org/), [official project](https://github.com/captbaritone/webamp))

The primary Webamp capture is Evidence `ev_98f798eb06cb7c017042aaa8faaff4f2322dc5d7ca653ae05f824d6a27d23052`; the click capture is `ev_06895eef3bc720f3d412d6d66e0e766e373e7985c899186c7c9512a1bb90bc14`. **Poolsuite demonstrates consistency across several small experiences.** REA captured a stopped player with an explicit Play control, track/channel labels, a video filename, clock and dock entries including Player, Newsroom, Mixtapes and Guestbook. ## Dithering and ASCII can define the site without taking it over

The most economical visual system is **a small palette shared by images, interface and one ASCII artwork**. Your earlier retro-window direction can evolve without making every link a draggable window. These are three original directions to choose between, not settled designs.

| Direction | What visitors enter | How your ideas fit | Main cost |
|---|---|---|---|
| Personal lab desktop | A personal computer with ordinary flowing panels styled as windows | Dithered wallpaper/portrait, project folder, notepad, ASCII diagnostics, music window | Familiar to your current direction; full window dragging/overlap would add mobile and focus complexity. |
| Robotics workbench | A bench with labels, sketches, parts and project specimens | Dithered bench images, an ASCII arm, paper-like notes, a shared robot-power/boop control | Most closely tied to your interests; illustrated exploration needs conventional text navigation too. |
| Signals from Lucas | A personal transmission station or terminal | Dithered transmitted portrait, ASCII signal, thought log, project archive, listening station | Compact and readable; personal photos and writing must distinguish it from a generic terminal portfolio. |

### Dither selected media before publishing

**Difficulty: small. Dependencies: an image editor or existing command-line tool, with no browser library required.** Start with a real portrait and one robot/bench detail. Preserve originals, crop for the eventual composition, reduce the resolution deliberately and convert to a two- or four-color palette. Compare an ordered/Bayer texture with Floyd–Steinberg rather than assuming one fits every image. GIMP documents indexed palettes and Floyd–Steinberg choices; ImageMagick documents palette reduction, remapping and ordered threshold patterns. ([GIMP manual](https://docs.gimp.org/2.10/en/gimp-image-convert-indexed.html), [ImageMagick options](https://imagemagick.org/command-line-options/))

Export PNGs and compare actual sizes. Dithering is not a guarantee of smaller files. For animation, a stable ordered pattern can avoid changing noise, a point illustrated by ImageMagick's [video examples](https://usage.imagemagick.org/video/). CSS `image-rendering: pixelated` helps scaling; **it does not create dithering**. Fractional scaling can still produce uneven-looking pixels. Keep body text sharp and readable, preserve descriptive alt text and offer a detailed original when wiring labels or diagrams matter. ([MDN image rendering](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/image-rendering), [pixel-art guidance](https://developer.mozilla.org/en-US/docs/Games/Techniques/Crisp_pixel_art_look))

Candidate palettes include charcoal/cream/amber, ink/cream/acid green or a stricter four-tone version of your earthy colors. Those choices need a visual comparison later. A live dither shader is an optional second experiment: apvl.dev documents a music-reactive dithered noise background, but that does not mean your first version needs its Three.js stack. ([Author's write-up](https://apvl.dev/stuff/personal-portfolio/))

### Give one ASCII object a useful personality

**Difficulty: medium. Dependencies: plain JavaScript is enough for a monochrome grid.** A robot head whose eyes follow the pointer and whose expression changes on tap is a stronger personal starting point than a generic matrix rain effect. Alternatives are a two-link arm following a target, a rotating wireframe gear or a signal field disturbed by the cursor. ASCII Play's manual documents the core method: calculate a character per cell, account for character aspect ratio and use pointer coordinates as input. Its text/canvas renderer tradeoff is documented; performance on your visitors' machines was not measured. ([ASCII Play manual](https://play.ertdfgcvb.xyz/abc.html))

The later implementation can keep one `frame(time, pointer, width, height)` calculation and update a single text block. A starting design budget of roughly 64×24 cells and 15–24 updates per second is a proposal, not a benchmark. Use elapsed time, cap updates and stop work when hidden/offscreen. `requestAnimationFrame` supplies the browser animation callback; Pointer Events cover mouse, pen and touch. Avoid thousands of DOM elements unless measured needs justify per-cell styling. ([MDN animation](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame), [Pointer Events](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events))

Put Play/Pause and expression/reset buttons beside the artwork. Reduced motion should start with a still image. Keep constantly changing ASCII out of live regions; decorative art can be hidden from assistive technology, with meaningful text nearby. If the toy communicates a state, also expose that state in text. On phones, reduce cell count to fit the panel rather than shrinking every character into illegibility, and do not intercept ordinary scrolling. A focused arrow-key alternative can complement pointer input without hijacking page-wide typing. Ongoing nonessential animation and drag-only interaction have explicit accessibility considerations. ([Reduced motion](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion), [WCAG pause/stop/hide](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html), [dragging movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html))

### Make the hidden detail a reward

**Difficulty: small to medium. Dependencies: none beyond the page.** An “Inspect loose screw” button could reveal an ASCII pet or build blooper; a diagnostics badge could show a fictional sensor joke alongside a real build date; a lost-parts 404 page could contain a tiny toy and a reliable home link. A secret keyboard sequence can toggle a blueprint palette, provided touch users have another route and Escape restores the usual view. These are proposed ideas, not claims about hidden features on the reference sites.

Discovery stamps can record three or four finds in localStorage, but only for that browser. Essential project, contact and ring navigation must remain visible. Avoid surprise audio, flashing effects or actually closing the site as a joke. Aster's explicit plaintext sitemap is the useful precedent: exploration can coexist with direct access. ([Aster's Archive](https://astersarchive.neocities.org/Home))

## Projects and small thoughts will make people return

**An empty project shelf is better than invented projects.** Give Projects a real destination and an honest message such as “Making room for things I build.” If there is actual unfinished work you want to show, label it an experiment and say what currently works. The future entry shape only needs a title, image or ASCII preview, one-sentence purpose, honest status and available links. A later write-up can explain the question, build, mistakes, photographs and next step. Search, filtering and a CMS have little value before there are entries. This is a proposed content model, informed by the projects/thoughts combination in [apvl.dev's write-up](https://apvl.dev/stuff/personal-portfolio/).

### Make quick notes easier to publish than a blog essay

**Difficulty: small. Persistence: Markdown/JSON in Git, not a visitor database.** Call the stream “Brain buffer,” “Bench scraps” or simply “Notes.” Each entry gets a date and text; a title is optional. Show the latest three to five on the homepage, with a permanent archive. The smallest authoring workflow is editing one Markdown file or a small entries folder locally or through GitHub's web editor, previewing and deliberately publishing. That workflow is proposed, not configured here. Status Cafe demonstrates timestamped short thoughts, while Maggie Appleton explains revisable connected ideas and cautions against confusing gardening with technical graph features. ([Status Cafe](https://status.cafe/), [garden history](https://maggieappleton.com/garden-history), [nontechnical gardening](https://maggieappleton.com/nontechnical-gardening))

Public notes and visitor writes are different needs. Do not introduce an admin dashboard just because the site also has a global counter. Try the Git workflow first; if it feels too slow for the frequency you actually want, evaluate authenticated posting later. Keep private drafts out of the public repository until you intend to publish them. A separate `/now` page can describe what you are building, studying, reading and listening to, with a real last-updated date. A chronological thought stream and a current-life snapshot serve different readers. ([Sivers's /now](https://sive.rs/now), [convention explained](https://nownownow.com/about))

Some of these span several eras of the personal web. “Web 1.0” is a useful mood here, not a requirement to reproduce historical limitations. Clear links, small personal collections and visible connections to other sites deliver more of that mood than tiny fonts, constant marquees or cursor trails everywhere.

## One shared number and one music window are enough infrastructure

### Make the number honest and intentionally playful

**Recommended first interaction: “Boop the robot,” with a shared total of accepted boops.** It gives a visitor something to do and satisfies the database idea without claiming to identify unique humans. An odometer of pageviews is another option, but visits, reloads, bots and blocked analytics complicate its meaning. [Applause Button](https://applause-button.com/) documents the frontend-plus-cloud-endpoint pattern for persistent claps; no service writes or current privacy review were performed. [GoatCounter](https://www.goatcounter.com/help/visitor-counter) documents public HTML/SVG/PNG/JSON counters with explicit enablement, per-path/total values and caching up to four hours. That suits a slowly updated pageview display rather than immediate click feedback.

| Storage choice | Good use here | Boundary |
|---|---|---|
| Markdown/JSON | Your notes, project entries, links and changelog | Public authored content; no live visitor writes. |
| localStorage | Theme, volume, discovered stamps, recent-boop UI hint | Browser-local, clearable and not a global count or trustworthy vote limit. |
| Existing analytics counter | A displayed count of recorded pageviews | Can lag; does not provide the requested intentional click interaction. |
| Static site + Cloudflare Worker + D1 | One custom shared boop total | Suggested minimum backend: two API routes, one table, server validation. |
| Static site + Supabase Edge Function + Postgres | Multiple future tables or a moderated guestbook workflow | Reasonable if familiar already; requires grants/RLS/endpoint permissions and server-side protections. |

GitHub Pages serves static HTML/CSS/JavaScript, so database writes need an external endpoint. Worker bindings can connect a Worker to D1 without account credentials in the frontend; D1 documents parameterized prepared statements. Supabase distinguishes publishable keys from privileged server secrets, and its Data API protection requires grants plus RLS. **Never ship a privileged database/service key in browser code or commit it.** No current price, quota or free-tier promise is made; check those when implementing. ([GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages), [Worker bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/), [D1 statements](https://developers.cloudflare.com/d1/worker-api/prepared-statements/), [Supabase keys](https://supabase.com/docs/guides/getting-started/api-keys), [Data API security](https://supabase.com/docs/guides/api/securing-your-api), [Edge Functions](https://supabase.com/docs/guides/functions))

**Difficulty: medium.** Seed one `counters` row with a fixed name and nonnegative integer. `GET /boops` reads it; `POST /boops` increments that fixed counter by exactly one. Do not accept arbitrary deltas, table names or counter names from the browser. Use one database mutation such as `UPDATE counters SET value = value + 1 WHERE name = ?1 RETURNING value`, binding the known name; a missing seed row is an error. Reading an old value in browser JavaScript and writing back `old + 1` loses concurrent increments. This SQL is a planning sketch, not tested implementation. ([D1 prepared statements](https://developers.cloudflare.com/d1/worker-api/prepared-statements/), [SQLite RETURNING](https://www.sqlite.org/lang_returning.html))

Throttle bursts server-side, reject unexpected methods/parameters and bound request size. A local cooldown is useful feedback but is bypassable; CORS is not authentication for direct requests. Cloudflare documents that its rate limiter is approximate and local to a location, and that IP limits can group legitimate users. Purdue users can share networks, so avoid calling an IP limit “one vote per person.” Show pending state and the server-confirmed total; if unavailable, keep a labeled last-known value or say “counter offline.” Do not silently replace failure with zero or blindly retry an uncertain POST. Exact-once intended votes would need request IDs and database deduplication; an approximate toy does not need that promise. ([Workers rate limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/))

Keep resets private, expose only the aggregate and review provider logging before writing a truthful short privacy note. Use a real button, visible focus and readable status feedback. Before eventual launch, test concurrent increments, malformed requests, throttling and outage behavior. Arbitrary guestbook text brings a separate moderation job: server-side length rules, plain-text storage/escaped display, approval before publication and deletion controls. A number avoids that entire first-version burden. localStorage can fail or be unavailable, so UI preferences must tolerate exceptions. ([MDN localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage))

### Use Webamp when Winamp itself is the feature

**Difficulty: medium for integration; higher for a custom skin/visualizer and robust floating layout. Dependency: Webamp, if chosen.** The official MIT code license does not automatically license Winamp branding, every skin or sample song. Start with a small playlist you own or are clearly permitted to distribute; a reachable MP3 URL is not permission to rehost it. Otherwise offer a permitted platform embed or link. ([Webamp project and licensing](https://github.com/captbaritone/webamp))

The proposed flow is a semantic “Open radio” button that loads Webamp on demand and creates one instance. Official constructor options cover `initialTracks`, skins and layout. Supply metadata/duration and appropriately served media URLs; cross-origin assets need correct headers. Use `renderInto` for a positioned parent when appropriate, or understand that `renderWhenReady(container)` locates the default body-appended player rather than necessarily containing it. Keep a fallback when the player cannot load. ([Constructor API](https://docs.webamp.org/docs/api/webamp-constructor/), [initialization](https://docs.webamp.org/docs/initialization/))

Let visitors explicitly press Play. Browsers restrict audible autoplay, so handle rejected playback and broken URLs with readable controls. A video autoplay attribute is not evidence of audible music, including in the Poolsuite capture. On phones keep controls in the viewport or use a compact native `<audio controls>` alternative; do not reduce an entire desktop player to unusably tiny buttons. Save volume locally only if useful, keep global hotkeys out of text inputs and reduce visualizer work when hidden or reduced motion is requested. ([MDN autoplay](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay), [reduced motion](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion))

A single page with panels simplifies uninterrupted listening; separate full-page navigation needs a deliberate continuity approach. apvl.dev documents its Astro routing solution, but your site need not adopt that stack just for music. A three-to-six-track rotation or original ambient loop is enough; there is no need to recreate a radio service. Current package version, bundle size, final track/skin permissions, hosting headers and mobile layout remain implementation-time checks. ([apvl.dev write-up](https://apvl.dev/stuff/personal-portfolio/))

### Build priorities should follow personality and maintenance

| Priority | Proposed scope | Why |
|---|---|---|
| First | Choose one setting/palette; real introduction, direct navigation, project destination, Markdown notes, dithered portrait, visible ring links | Establishes an actual personal site and a repeatable publishing workflow. |
| First signature | One ASCII robot/arm/signal and one modest hidden detail | Supplies the moving/interacting personality without competing animations. |
| Next | One shared boop total; Webamp if music is a central interest | Addresses your two service/integration ideas with isolated failure states. Both remain in scope for the eventual desired site. |
| Later | RSS, own button/friends shelf, `/now`, discovery stamps, more project stories | Adds reasons to return after the first content exists. |
| Only with a reason | Guestbook, poll, live dither shader, custom music skin, authenticated note editor | Each adds moderation, service or rendering work; choose based on actual use. |
| Skip initially | Full OS/window manager, custom audio engine, graph database, public arbitrary-text posting, fake projects, uniqueness claims | None is necessary to deliver the ideas you requested. |

These are sequencing recommendations, not a reduced specification or a commitment to an aesthetic. Before designing, the useful open decisions are **which place the site should feel like**, how dense/playful it should be, how professional versus personal the writing should feel, what music you can share and whether the shared number should represent boops or pageviews. None requires permission to keep researching; they shape the next creative conversation.

The most durable source of interest will be your own photos, notes, unfinished experiments and chosen links. A coherent surface makes those inviting; one artwork makes the site memorable; a small shared action lets a visitor leave a trace. That division keeps the site expressive while leaving enough energy to keep adding things after launch.

**Unchecked:** no implementation, deployment, backend writes, audio listening, visual screenshot review or device/accessibility audit. Runtime evidence is deliberately bounded, especially Windows93. **Before eventual release:** verify chosen assets' permissions, service settings and logging, concurrent counter behavior, phone/keyboard/reduced-motion use and live ring navigation. The research is a design basis, not a tested production implementation.
