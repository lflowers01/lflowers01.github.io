# Personal portfolio reference library

**October 18, 2026 · Research and reconstruction planning only.** A personal Web 1.0 portfolio can express many personalities: an orderly hand-coded home, a crowded pixel dollhouse, an ASCII terminal, a fan shrine, a workstation or a little radio hut. The useful common thread is authored content, visible neighbors and small discoveries. This library expands the earlier references with more personal sites and bounded technical studies while keeping your original list intact. Its five chapters contain **12 design-language cards, 18 interactive-element recipes and 19 content/community recipes**, plus 16 short visual patterns and **14 further reconstruction recipes drawn from the Purdue ring**. Those are entry counts, not unique features; related ideas intentionally appear in several contexts. The [browsing index](../README.md) connects examples to recipes so that you can select a coherent site later rather than implement this entire collection.

## Variety comes from different kinds of personal places

The [design chapter](../library/design-languages.md) distinguishes GeoCities maximalism, handcrafted HTML, terminal/BBS, Windows desktop, ornate pixel home, illustrated room, scrapbook/zine, shrine, dithered transmission, portal, player skin and community instrument. These are analytical categories, not labels claimed by the creators. The differences are practical: an index invites reading; a room invites exploration; a shrine invites depth on one interest; a desktop turns destinations into familiar objects. A portfolio can use any of these structures while keeping projects understandable.

The new references add breadth inside the old-web focus. Neustadt explicitly describes a tribute to the creative 1990s web; Cyber Vanguard groups technical interests, diary and links; cinni organizes many interests inside a personal home; fauux explains a dithered style tied to early storage constraints. These are different reasons for a site to look handmade. The library also retains earlier apvl, Xiokka, Aster, Cameron's World, Webamp and Poolsuite research, rather than treating the new collection as a replacement. ([Neustadt](https://neustadt.fr/), [Cyber Vanguard](https://cyber.dabamos.de/), [cinni](https://cinni.net/), [fauux](https://fauux.neocities.org/))

Content references broaden the vocabulary further. PIXELDEW's herbarium, recipes and toyboxes suggest a hobby archive; purgamentum exit's postcards and collections suggest a personal correspondence shelf; Kerka's chronological log suggests visible ongoing care. These examples make room for unfinished interests alongside a professional introduction. The library deliberately avoids requiring a modern agency-style portfolio or pretending that every old-web site is visually interchangeable. Page retrieval establishes the linked content and labels; it does not certify their rendered appearance or usability. ([PIXELDEW](https://pixeldew.nekoweb.org/pages/home.html), [purgamentum exit](https://notprincehamlet.neocities.org/), [Kerka](https://kerka.neocities.org/log/))

A **robot workshop** could use dithered photographs, parts-drawer project links, a compact ASCII mechanism, bench-scrap notes and a shared robot-power total. An illustrated object can be an extra entrance while ordinary text links remain visible. This is a strong fit if robotics is the part of yourself you want to foreground; it is not an assumption that every page must be engineering-themed. ([Aster's Archive](https://astersarchive.neocities.org/Home))

A **dorm computer** could put projects in a folder, short thoughts in a Notepad-like panel, and music in Webamp. Windows can remain in normal document flow until movement adds real value. A **radio outpost** could connect a dithered transmission portrait, ASCII signal field, station log, playlist and tuning-panel easter egg. A **pixel scrapbook** could combine original stamps, a hobby shrine, photos, a friends shelf and a small adoptable robot. These are proposed combinations, not descriptions of a single reference or decisions already made for you.

All the original requested elements have practical routes. Dithering can happen before publishing rather than in a heavy live shader. Interactive ASCII can use one character grid driven by elapsed time and pointer state; the donut author's explanation provides projection, depth and lighting mathematics. Future projects can use an honest shelf and real status labels; the history chapter identifies ten existing archived cards to consider before assuming the shelf is empty. Quick notes can be dated Markdown entries, while an easter egg can reveal a toy or stamp without hiding necessary navigation. Music can use Webamp when Winamp itself matters, or native audio behind an original cassette skin. ([ASCII Play manual](https://play.ertdfgcvb.xyz/abc.html), [donut explanation](https://www.a1k0n.net/2011/07/20/donut-math.html), [Webamp documentation](https://docs.webamp.org/docs/api/webamp-constructor/))

The [interactive chapter](../library/interactive-elements.md) adds pointer reveals, follower sprites, dust, trails, starfields, CRT treatments, skins, small games and optional command prompts. The [community chapter](../library/community-and-content.md) adds shrines, changelogs, friends buttons, cliques, guestbooks, polls, pixel quilts, feeds, mailbox links and shuffle. ## Storage choices determine maintenance more than visual style

**Authored content, browser preferences and shared visitor state are different things.** Projects, notes, links, playlists and changelogs can be static files. Themes, volume and discovery stamps can be browser-local and clearable. A shared boop total, pet or poll needs a server-side operation and database. GitHub Pages serves static content; frontend JavaScript alone cannot safely become that shared database. ([GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages))

A boop total is a clearer first shared toy than an unqualified “visitor” number. It counts accepted actions. The recipe calls for a fixed counter ID, atomic increment, bounded requests, server throttling, private resets and visible pending/failure states. Pageviews remain an alternative with provider-defined metrics and caching. Browser cooldowns are convenience controls, not proof of one person per action. A guestbook or mural introduces public-content moderation and recovery work beyond the numeric toy. No backend, service account or public write was created here. ([D1 statements](https://developers.cloudflare.com/d1/worker-api/prepared-statements/), [GoatCounter counters](https://www.goatcounter.com/help/visitor-counter))

Later implementation should establish the reading structure, real introduction, project destination and note workflow first; then one palette/asset kit, one ASCII artwork and an optional secret. Music and shared persistence deserve isolated integrations with their own error states. Keep the Purdue ring links visible from the beginning, then verify production behavior and follow its joining process only after publishing. A research branch is not an alternate hosted site. ([Purdue Hackers joining instructions](https://github.com/purduehackers/webring#want-to-join))

## Keep the library useful as references change

Use the [index](../README.md) to shortlist one organizing world, two complementary references and a small set of elements. Preserve the source link, inspection date, evidence label and permission notes when adding a reference. A failed fetch should remain a lead rather than becoming a verified example; Melonking's closure message and the original Windows93 loading/certificate limits show why this matters. Site changes can invalidate an old observation without invalidating the underlying idea.

The eventual site's strongest material will be your own writing, photographs, experiments and chosen neighbors. Technical recipes make the visual ideas achievable; they do not replace those personal decisions. This work has not built or deployed a site, chosen final assets, audited licenses, listened to audio, tested mobile/assistive technology, or verified backend operations. Those checks should follow the concrete features you select rather than turning an inspiration library into an invented production guarantee.
